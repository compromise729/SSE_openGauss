# LZM-03｜尚未解决及临时处理问题与后续修改建议

源码与工具输出提交：`0671a79d068b8c3535b7c511c4aeefe76710a032`；分支：`test/LZM-03-state-crypto`。本地提交内容已与实测指纹核对一致。

日期：2026-11-19。

本文保留 `0671a79` 原始交付的观察和建议。原生构建、验证入口及重插回滚的更新见 [契约修复与原生复验](契约修复与原生复验.md)。后续团队继续跟进第六节的故障覆盖、发布环境部署和跨端恢复。

## 一、安装的数据库程序仍未更新为支持新版入口的产物

**当前问题：** 仓库源码已有 fides_v1_select，但当前安装的旧 gaussdb 不包含该入口。更新源码不会自动更新可执行程序。完整原生发布包的构建与验收尚未完成。

**本轮处理：** 重新编译服务端相关源码，链接独立 gaussdb，在私有挂载命名空间中供本次隔离实例使用。原安装程序保持原样。

**后续建议：** 从同一固定源码版本，使用正常项目构建流程生成配套 gaussdb、gsql、完整 libpq 和 SSE_v1.sql，放入独立发布目录。先验证这套产物，再安排正式部署。无需为此升级系统依赖；现有安装目录是否更新单独决定。

**验收标准：** 指定发布目录的程序能完成新版建表、插入、真实 Fides 搜索和重插；不依赖把新程序临时绑定到旧安装路径。记录程序和 SQL 的源码版本、SHA-256。

## 二、验证时仍使用新模块与原 libpq 并存的布局

**当前问题：** 为保持已安装 libpq 原样，本轮构建 librow_request_verify.so 提供当前请求、状态和密码实现，再与原 libpq 配合验证。这还不是完整原生库的发布验收。

该布局曾导致 Client_Sophos.cpp 中 storage_dir_path 全局对象重复构造/析构，初始化成功后进程退出时 Aborted。

**本轮处理：** 构建器生成临时 Client_Sophos 副本，将该全局定义改为 extern，复用原库对象。此处理避免了验证进程中的重复析构。

**后续建议：** 正常构建完整 libpq，使 Client_Sophos.cpp 只编译、链接一次；gsql 直接链接同批完整库。移除验证构建器中的源码复制和全局定义文本替换，也不再依靠补充业务模块覆盖旧实现。故障注入库继续作为测试工具使用。

**验收标准：** 普通业务启动不需要 librow_request_verify.so；不进行源码文本替换；客户端初始化、反复请求和退出均正常，进程实际加载的库来自指定发布目录。

## 三、临时构建器依赖现有对象和 make 输出格式

**当前问题：** preflight/build-live.py 通过 make -n 获取命令、复用本机已有 .o，再重新编译部分源码。脚本还包含当前编译器、依赖目录和链接命令格式的假设。尚未验证从全新构建目录生成整套原生产物。

**本轮处理：** 使用当前工程的已有构建参数和对象完成验证，没有修改安装环境。

**后续建议：** 将完整编译、依赖关系和打包交给项目原生构建目标。验证脚本负责调用构建目标及检查结果，不长期解析 make 输出、替换链接参数或手工补入对象。若使用构建缓存，应把源码、编译器、依赖和编译选项纳入缓存标识。

**验收标准：** 在具备团队既定依赖的干净构建目录中可以复现；不存在旧对象混入新版本的情况；产物记录完整输入版本，构建失败明确返回非零。

## 四、验证入口还不能直接验收外部提供的正式产物

**当前问题：** verify-all.sh 自动调用当前临时构建器；run-live.sh 通过绑定临时 gaussdb 使用旧安装路径；live-cases.py 的管理查询仍从 repo/dest/bin/gsql 调用程序。因此当前工具还不能完整证明“组长提供的某个发布包”自身可用。

**后续建议：** 给验证入口增加明确的发布目录参数，将“构建”和“验证”分开。客户端、服务端、配套库和管理查询都从该目录选择，设置仅对子进程生效的运行路径。目录隔离继续保留；编译进二进制的状态挂载目标仍须核对，不能由 checkout 位置猜测。

**验收标准：** 同一组测试可直接针对指定发布包执行；日志列出实际程序与加载库路径；缺组件或版本不匹配时在实验准备前拒绝，不静默回退到旧安装程序。

## 五、令牌故障注入依赖 C++ 修饰符号名

**当前问题：** live-fault-hook.cpp 通过 dlsym 查找 SophosClient::search_request 的具体修饰符号。这与当前 C++ ABI 和签名绑定，后续接口调整可能使测试钩子失效。

**本轮处理：** 固定当前编译 ABI，在真实令牌生成之后注入空 token/derivation_key，两个实际请求用例通过。

**后续建议：** 为测试提供明确的令牌生成适配接口或测试构建专用注入点。正常实现调用真实 Fides；故障测试在该接口上替换结果。注入功能默认关闭，不用于普通业务启动。

**验收标准：** 测试不依赖手写的 C++ 修饰名；普通业务不启用故障注入；异常空令牌、正常未知词、坏状态继续返回不同结果，并保持无错误计数推进。

## 六、实际客户端的部分故障覆盖仍待补齐

**当前情况：** 本轮真实客户端已覆盖标记替换失败、缺钥、坏状态、空令牌和重插 SQL 失败。以下机制有状态模块级验证或代码分支，但尚未全部在本轮真实客户端链路再次注入：

| 待补验证 | 建议验证内容 | 通过标准 |
| --- | --- | --- |
| 第二客户端竞争 | 第一客户端持有真实活动操作时启动第二客户端。 | 第二客户端 busy，无计数推进或业务发送，不清除第一客户端标记。 |
| 状态持久化失败 | 分别注入写入、文件同步、替换和目录同步错误。 | 返回失败、保留标记、停止后续请求，不展示准备中的业务结果。 |
| 完成标记清除失败 | 注入删除或清除后的目录同步错误。 | complete 返回失败，不展示结果；新进程仍可靠阻断。 |
| 处理中强制退出 | 在实际索引取出或重插阶段终止客户端。 | 保留现场，新进程识别未完成操作，不盲目重试。 |
| 服务端重启 | 保留同一套密钥、计数和映射，重启后执行必要 setup。 | 查询集合和重复次数正确，状态延续，未换钥或重建。 |

这些属于后续真实链路故障和恢复验收，应在组长公布的新固定版本上执行。不能把原有模块测试直接记为上述真实客户端用例通过。

## 七、真实重插失败后的索引缺口仍然存在

**当前情况：** LIVE-15 中索引已被取出，随后重插失败。故障发生后业务数据仍有4行，索引只剩2行。当前实现停止回查/展示、保留标记，并在客户端重开时阻断；没有恢复已经取出的索引。

**后续建议：** 在后续恢复任务中提供基于完整数据库和客户端状态证据的人工诊断流程，说明何时只能重建新的可丢弃测试环境。自动恢复、安全重试或跨端事务需要另外设计，不通过删除标记、重新 setup 或换钥实现。

**验收标准：** 故障现场可追溯，未完成操作持续阻断。只有经过明确设计和验证的恢复流程才能继续业务；当前单文件原子替换不被描述为跨端事务。
